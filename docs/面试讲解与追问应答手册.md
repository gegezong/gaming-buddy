## 0. 开场话术

### 30 秒电梯陈述

> 我做了一个游戏陪玩交易平台「一起开黑吧」，技术栈是 FastAPI + Vue3。
> 业务侧我设计了 28 张表覆盖用户、陪玩师、订单、钱包、优惠券全链路，用 RBAC 加 JWT 做了管理员、普通用户、陪玩师、客服四类角色隔离，订单支付用数据库事务保证资金一致性。
> AI 侧是基于 LangGraph Supervisor 搭的两套多智能体系统：面向 C 端用户的智能助手和面向 B 端老板的经营分析助手。NL2SQL 那块我做了多层安全沙箱，订单工具用闭包绑定 user_id 防横向越权，流式输出走 SSE 加 Token 增量。

### 3 分钟完整版（按这个顺序讲，不要按简历条目顺序）

1. **业务背景**：陪玩是一个典型的双边交易平台，复杂度在于「资金 + 排期 + 实时沟通 + 售后」四条线同时存在。
2. **先讲业务链路**：浏览陪玩师 → 下单预约 → 余额/优惠券支付 → 开始服务 → 评价/打赏 → 投诉退款。这条链路上有 **28 张表**。
3. **再讲 AI 差异化**：这个平台真正的痛点不是「没有信息」，而是「信息散落在 28 张表里，用户不知道该怎么问」。所以我做了两个 Agent 场景：C 端帮用户「找到合适的人 + 查自己的订单资产」，B 端帮运营「用自然语言看经营数据」。
4. **重点强调安全**：AI 能查业务数据、能执行 SQL，这是权限边界最容易塌方的地方，所以我把「安全约束放在执行层，不依赖提示词」。
5. **收尾**：整条链路我都跑通了，包括 SSE 流式、实时聊天、后台看板。

## 1. 逐条讲解：简历第一句「业务系统与权限控制」

### 1.1 你在讲什么

这一条对应简历第一个 bullet，拆成三块：**数据建模**、**权限控制**、**事务一致性**。面试官听到「28 张表」时，真正想听的是你怎么划分的边界，而不是数字本身。

### 1.2 怎么讲（照着说）

> 我按业务域把表分成六组：用户与权限 4 张（user / role / menu / role_menu）、陪玩与内容 6 张、交易与订单 2 张、营销与资金 5 张、沟通服务 5 张、运营与 AI 6 张，正好 28 张。
>
> 这里有个设计取舍要说明：**陪玩师和用户共用一张 user 表**，通过 role_id 区分角色，但陪玩师的业务档案单独放在 companion 表，两张表用 user_id 一对一关联。好处是登录、鉴权、消息这些横切能力只需要做一套，不用在两套用户体系里重复实现；代价是陪玩师档案和账号之间要处理同步问题。
>
> 权限是 RBAC：role 表定角色，menu 表定功能点，role_menu 是关联表。用户登录后拿到的 JWT 里带了用户快照（含 roleId），菜单查询时按 role_id join role_menu 做过滤，管理员角色直接跳过过滤看全部菜单。前端的后台路由是**根据这个菜单接口动态生成的**，所以四类角色登录后看到的菜单和路由完全不一样。
>
> 事务这块，核心是支付链路。余额支付要在一个事务里做三件事：扣余额、写钱包流水、置订单状态为已支付。而且如果订单用了优惠券，核销券我用的是**条件更新**——`where status=0 and expire_time >= now()`，然后检查 rowcount，如果更新了 0 行说明券已经被并发核销掉了，这时候 `db.rollback()` 把已经扣掉的余额退回去，然后提示用户重新下单。不会出现「钱扣了但券还能用」的脏状态。

### 1.3 面试官可能追问 + 标准答法

**Q1：为什么陪玩师和用户共用一张 user 表？分开不是更清晰？**

> 选共用是因为这个系统里陪玩师**同时也是平台用户**——他会用普通用户身份浏览游戏、下单买其他陪玩师，也会收到用户私信。他需要一个统一账号体系来处理登录态、消息通道、钱包这些横切能力。
> 分表的话这些能力要么建两套，要么加一层「用户表 + 角色扩展表」的判别联合，反而更绕。
> 我用的是共享主键 + 一对一扩展表，业界也是这个模式（比如 Shopify 的 merchant 和 user）。
> 如果要更进一步，可以在 user 上加一个「一人多角色」的能力，但当前业务里一个账号只有一个角色，扩展表的方式足够了。

**Q2：JWT 里存了用户信息，角色改了怎么立即生效？**

> 这是 JWT 无状态设计的经典代价。我的处理方式是**接受这个延迟**：token 里带了 `expireTime`，还有退出登录的黑名单机制。
> 更严格的做法有两个：一个是缩短 token 有效期（比如 30 分钟）配合 refresh token，用户感知不到但服务端能定期重新校验；另一个是把「角色 → 权限」这类高频变更数据放 Redis，每次校验时查一次。
> 当前实现里，角色变更后需要等 token 自然过期或用户重新登录才生效。对运营后台来说这个延迟可接受，因为改角色是低频操作。生产化我会加 Redis 缓存角色版本号，token 里带版本号做一致性校验。

**Q3：你的密码怎么存的？**（⚠️ 这是必问题，见第 4 节软肋）

**Q4：并发下单会不会超卖？**

> 这里要分两层看。**时间段冲突**我做了防重：下单时校验「同一陪玩师 + 同一天 + 同一开始时段」是否已有活跃订单（`status in (booked, ongoing, completed, refunding)`），有就直接拒绝。
> **金额层面**我用了服务端定价：订单单价不是前端传的，是我从 `companion_service` 表查出来的 `svc.price * hours`，前端传的价格字段根本不参与计算，从根上杜绝了篡改。
> 但我要坦白一点：**余额扣减那一步目前是「先读后写」，没有加行锁**。两个并发支付请求理论上可能出现都读到余额充足、各自算出扣款后余额、导致少扣或者扣成负数的情况。正确做法是 `SELECT ... FOR UPDATE` 锁住用户行，或者用 `UPDATE user SET balance = balance - ? WHERE user_id = ? AND balance >= ?` 让数据库用受影响行数做乐观并发判断。这是我后续一定要补的点。

**Q5：JWT 用的什么算法？为什么 HS512？**

> HS512，对称加密，密钥由服务端持有。选它是因为当前是单体服务，签发和校验在同一个进程，不需要非对称。JWT 里 `exp` 用标准秒级声明，签名用 HS512 保证防篡改。
> 如果以后要拆成多服务或者第三方接入，HS512 就得换成 RS256 这类非对称方案，让各服务只持有公钥就能验签。

**Q6：为什么不用 Session？**

> 要支持 SSE 长连接和 WebSocket 长连接，同时后端是无状态的、后面要横向扩展，所以选了 JWT。
> 代价是没法主动吊销，我用了一个内存黑名单兜底——但这个黑名单是**进程内存**的，多 worker 或重启就失效了。这是已知缺陷，生产化应该放 Redis。

## 2. 逐条讲解：简历第二句「多 Agent 工作流」

### 2.1 你在讲什么

这是**整个项目的技术核心**，也是面试官刨得最深的一块。讲之前先想清楚一个问题：**为什么是多 Agent，不是一个 Agent 写几个工具？**

### 2.2 为什么选 Supervisor 模式（这段一定要讲透）

我实测了编译后的图结构：

```
用户端场景                          管理端场景
节点: __start__ → supervisor        节点: __start__ → supervisor
      recommendation_agent                metrics_agent
      order_agent                         sql_agent
      faq_agent
边:   supervisor → {3 个子 Agent}      边:   supervisor → {2 个子 Agent}
      {3 个子 Agent} → supervisor           {2 个子 Agent} → supervisor
      supervisor → __end__                  supervisor → __end__
```

三个关键设计点：

**① 主管不带任何工具。** 它的唯一职责是「决定交给谁」。所有业务能力都在子 Agent 身上。这样主管的上下文永远干净，不会被工具返回的大段数据污染，路由决策的质量更高。

**② 边是条件边，不是写死的 if-else。** 路由由 LLM 主动调用移交工具（`transfer_to_order_agent`）的结果决定，是**模型决策**而不是硬编码分支。这是多 Agent 和「一个大模型 + 一堆工具」的本质区别。

**③ 子 Agent 执行完一定回到 supervisor。** 由主管统一组织最终答复再结束，保证用户只看到一个完整答案，而不是三个 Agent 各说一段。

**为什么是 Supervisor 而不是 Agent 自主协商（Swarm）？** 这是一个高频问��，我的答案：

> 自主协商的问题是**失控风险和不可预测性**。Agent 之间来回转消息，token 消耗不可控，容易出现死循环，而且你没法保证它一定能走到终点。
> Supervisor 模式是**中心化调度**：主管是唯一的路由决策点，子 Agent 是无状态的执行器。这样有几个实际好处：
> - **可控**：我可以精确控制子 Agent 数量和职责边界，加一个新能力就是加一个节点，不影响其他
> - **可观测**：每次移交都会产生 `transfer_to_xxx` 工具事件，前端能实时展示「已移交订单助手处理」
> - **可降级**：子 Agent 可以动态停用，主管自动接管，这是 Swarm 很难做的
>
> 代价是主管承担了所有路由决策的压力，如果任务复杂度远超「识别意图 + 分发」，Supervisor 就不太够用了，这时候应该换更复杂的编排。

### 2.3 共享状态是怎么实现的

> LangGraph 里共享状态就是 **`_OuterState`**，一个 TypedDict，里面只有 `messages` 字段，类型是 `Annotated[Sequence[AnyMessage], add_messages]`。
>
> `add_messages` 这个 reducer 的语义是「追加而非覆盖」——每个节点返回新消息时，自动合并到全局消息列表末尾，而不是把之前的历史冲掉。
>
> 移交的时候，handoff 工具内部执行的是 `Command(goto=[Send(agent_name, {**state, "messages": handoff_messages})])`，也就是把**当前完整状态**打包发给子 Agent。子 Agent 执行完返回，消息又通过 reducer 追加回全局列表。
>
> 所以协同的本质是：**通过共享消息列表传递上下文**。子 Agent 能看到主管和之前其他 Agent 的对话历史，这也是为什么子 Agent 的提示词里我要强调「不编造数据，只使用工具返回的真实信息」——它能看到别人的话，但必须以自己的工具结果为准。

### 2.4 面试官可能追问 + 标准答法

**Q1：Supervisor 和直接一个大模型挂 10 个工具，有什么区别？什么时候该用哪个？**

> 区别在**上下文控制和职责边界**。
>
> 单 Agent 多工具的问题：工具定义全在上下文里，每次请求都要过一遍；工具返回的数据会全量污染上下文；容易出现「LLM 在 10 个工具里选错」的情况。
>
> Supervisor 的优势：主管上下文只包含「有哪些助手可用 + 助手的一句话职责」，非常轻；每个子 Agent 只看到自己那 2-4 个工具，schema 更清晰，工具选择准确率更高；工具返回的数据在子 Agent 上下文里消化完，只把结论回传给主管。
>
> 什么时候用哪个：**工具数量少（< 5）、任务耦合度高、需要共享大量上下文**时用单 Agent；**工具多、能力域清晰、需要独立控制每个域的提示词和温度**时用 Supervisor。游戏陪玩这个场景正好是后者——推荐、订单资产、平台规则是三个明显独立的能力域。

**Q2：你怎么保证主管路由选对 Agent？**

> 三个手段：
> 1. **提示词里写死分派原则**。主管提示词明确写了「找陪玩师/推荐/比价 → recommendation_agent；订单/优惠券/钱包余额 → order_agent；平台规则/下单流程/售后/公告 → faq_agent」。这是最直接有效的手段。
> 2. **工具名自带语义**。移交工具名是 `transfer_to_order_agent` 这种，名字本身就说明了目标。
> 3. **子 Agent 失败可回退**。如果路由错了，子 Agent 的工具返回空结果，主管能根据结果重新分派。
>
> 另外我给不同 Agent 配了不同温度：主管 0.3（要稳定决策）、推荐 0.5（要多样性）、订单和 FAQ 都是 0.1（要准确不要发挥）。这也是一种控制手段——查账这种问题不该让模型自由发挥。

**Q3：子 Agent 怎么保证不越权？比如 order_agent 能不能查到别人的订单？**

> 用的是**闭包绑定**，这是我在安全设计上最满意的一点。
>
> `build_order_tools(user_id)` 这个工厂函数接收当前登录用户 ID，然后定义工具函数时把它**捕获进闭包**。工具的签名里根本没有 `user_id` 参数——LLM 看到的 schema 只有 `query_my_orders(status, limit)`。
>
> 这意味着：**LLM 从物理上就没有能力指定查谁的数据**。它就算在提示词注入里写「查询 user_id=999 的订单」，也构造不出这个参数。查询条件在函数体内写死为 `where user_id = <闭包捕获的ID>`。
>
> 这比「在提示词里告诉它只能查自己的数据」可靠得多——提示词约束是可以被绕过和越狱的，函数签名是代码层面的硬边界。

**Q4：一次对话可能触发几次 LLM 调用？成本和延迟怎么控制？**

> 一次「查订单」的用户提问，实际链路是：主管判断意图（1 次 LLM）→ 移交 order_agent → 子 Agent 决定调工具（1 次 LLM）→ 工具执行 → 子 Agent 组织答案（1 次 LLM）→ 回传主管 → 主管整合输出（1 次 LLM）。大概 3-4 次。
>
> 优化手段：
> - **output_mode="last_message"**：子 Agent 只回传最后一条消息，中间工具调用过程不进主管上下文，节省 token 也减少污染
> - **流式**：用户感知的是端到端时延，不是总时延，所以体感没那么慢
> - **工具结果截断**：所有工具返回值有 `_MAX_RESULT_CHARS` 上限（10000 字符），防止超长结果撑爆上下文
> - **上下文窗口**：只注入最近 20 条历史消息（`HISTORY_WINDOW = 20`）
>
> 还可以做但我没做的：意图识别用小模型、命中 FAQ 直接走缓存、相同查询的结果缓存。

**Q5：为什么用 DeepSeek？**

> 主要是成本和开源友好。用的是 `langchain-deepseek` 的 `ChatDeepSeek`，可以指向官方 API 也可以指向中转网关，配置项全在 `.env`。
>
> 有一个坑值得说：**我显式关闭了思考模式**（`extra_body={"thinking": {"type": "disabled"}}`）。原因是 DeepSeek 思考模式下，带 tools 的多轮请求必须完整回传 `reasoning_content`，而 LangChain 不会回传，DeepSeek 会直接报 400 错误。业务 Agent 也不需要思维链，关掉之后响应更快、更省 token。这是一个典型的「模型厂商特性 vs 框架抽象」冲突。

## 3. 逐条讲解：简历第三句「Agent 配置与会话管理」

### 3.1 怎么讲

> Agent 的提示词、温度、启停状态我存在 `agent_config` 表里，管理员在后台可以在线改，改完**下次对话立即生效，不用重启服务**。
>
> 这里有个关键设计：**代码是唯一事实来源，DB 只覆盖运行时可变部分**。我用了一个 `AgentSpec` 注册表（dataclass），每个 Agent 的 key、名称、场景、职责、默认提示词、默认温度、工具工厂全在这里注册。DB 里改提示词和温度，工具清单改不了——工具是代码注册的，管理页只读回显。
>
> 为什么这么分？因为**工具涉及权限边界**。如果工具能通过后台动态增删，那注册表里的闭包绑定、表白名单这些安全前提就可能被绕开了。所以我把「能改的」和「不能改的」明确切开：文案和参数可以热更新，能力和权限必须走代码评审。
>
> 装配流程是：每次请求构建图时，先从 DB 读场景下的 Agent 配置，读失败自动回退到注册表默认值；然后按 `enabled` 过滤（0 是启用，非 0 是停用）；提示词和温度 DB 优先，没有就回退默认。
>
> **降级兜底**是三层：
> 1. DB 读配置失败 → 全部回退注册表默认值，服务照常
> 2. DB 有记录但某字段为空 → 该字段回退默认
> 3. **某个子 Agent 被停用 → 它不进图，主管自动接管**；而且我会把「当前可用助手名单」拼进主管提示词，避免主管移交到一个已经停用的助手
> 4. **所有子 Agent 都停用 → 整张图退化成无工具的单 Agent**，主管直接对话并告知「相关能力维护中」，接口不会 500
>
> 会话持久化在 `agent_conversation` 和 `agent_message` 两张表。每轮请求先落库用户消息，再按会话 ID 拉最近 20 条历史转成 LangChain 消息二元组注入上下文。首轮自动生成会话标题。

### 3.2 面试官可能追问 + 标准答法

**Q1：每次请求都重建图，性能能接受吗？**

> 我算过这个成本：构建图主要是创建几个 `create_react_agent` 节点和一次 `create_supervisor` 编译，都是**纯内存对象组装**，不涉及网络 IO，也不涉及数据库写入（只有一次配置读取，且配置读取走了缓存思路）。
> 实际耗时在毫秒级，相比一次 LLM 调用动辄几百毫秒到几秒，可以忽略。
> 而且这样换来的是**配置改完立即生效**，不用重启也不用做缓存失效逻辑。
> 如果要优化，可以把图按「配置版本号」缓存起来，改配置时递增版本号，命中缓存直接复用、版本变了重建。这是我的下一步优化方向。

**Q2：会话存了数据库，但 LangGraph 不是有 checkpointer 吗？为什么不用？**

> 是个好问题。LangGraph 的 checkpointer 是给**图的执行状态**做持久化的，适合多轮对话恢复和 human-in-the-loop 审批中断这类场景。
> 我的场景是「应用层的会话记录」——用户要看会话列表、要看历史消息、要能删除某个会话，这些是产品功能，需要业务表来支撑。LangGraph 的 checkpointer 存的是内部 state 快照，不方便直接给前端渲染。
> 所以我用了 **DB 存业务会话 + 手工把历史转成 messages 注入** 的方式。好处是我完全掌控上下文窗口（只注入 20 条），能直接控制成本。
> 如果要做得更完整，可以两个都用：checkpointer 负责断点续跑，DB 负责产品展示。

**Q3：怎么防止用户 A 看到用户 B 的会话？**

> 三层校验，在 `routers/agent.py` 里：
> 1. **读会话列表**时按 `user_id` 过滤，只返回自己的
> 2. **读具体会话**时校验 `conv["userId"] != login_user.userId` 就抛「会话不存在」
> 3. **场景隔离**：用户端会话（scene=user）不能拿去管理端用，反之亦然，校验 `conv["scene"] != scene` 直接拒绝
> 4. 管理端场景额外走 `_require_admin` 校验，非管理员连会话列表都看不到
>
> 注意这里的错误文案是「会话不存在」而不是「无权访问」——不泄露「这个 ID 存在但不属于你」这个信息，避免 ID 遍历探测。

## 4. 逐条讲解：简历第四句「工具安全」

### 4.1 怎么讲（这是最能体现工程能力的部分）

> AI 能执行 SQL 是这个项目里**风险最高的一环**。我的核心观点是：**安全约束必须放在执行层，不能依赖提示词**。提示词里写「禁止删库」是建议，代码里拦住才是保证。
>
> 我基于 sqlparse 建了五层沙箱：
>
> **第一层，语句类型必须是 SELECT。** 用 `sqlparse.parse()` 解析后取 `get_type()`，不等于 SELECT 直接拒绝。INSERT/UPDATE/DELETE/DROP 全部挡掉。
>
> **第二层，禁止多语句。** 用 `sqlparse.split()` 切分，切出来不等于 1 条就拒绝。这是防「`SELECT 1; DROP TABLE user`」这种经典注入。
>
> **第三层，危险片段黑名单。** 正则拦截 `INTO OUTFILE`、`INTO DUMPFILE`、`FOR UPDATE`、`LOCK IN`、`LOAD_FILE`、`information_schema`，还有注释符 `--`、`/*`、`*/` 和分号。
>
> **第四层，表名白名单。** 这个是我觉得最重要的设计。我维护了一个 16 张业务表的 `_TABLE_SCHEMAS` 字典，里面每张表的字段、状态码含义、业务口径都写清楚了。SQL 里出现的表名必须全在这个白名单里，否则直接拒绝并把越权表名告诉 LLM 让它自己改。
> 顺便说一下，**`role`、`menu`、`role_menu` 这三张权限结构表故意不放进白名单**——管理端 Agent 完全不需要也不该查权限表。
>
> **第五层，结果限流与脱敏。** 没有 LIMIT 就自动包一层 `SELECT * FROM (...) AS _t LIMIT 1000`；返回结果里剔除 `password` 这类敏感列（不区分大小写，防止 `SELECT *` 把密码带出来）；JSON 结果超过 8000 字符直接截断，防止撑爆 LLM 上下文。
>
> 还有一个设计我觉得挺关键：**校验失败不抛异常，而是把错误信息当成工具返回值交还给 LLM**。返回 `{"error": "存在白名单之外的表: xxx", "hint": "请调整 SQL 后重试"}`。这样 LLM 能看到自己错在哪、自己改一版重试，而不是整个流程直接挂掉。这把「安全拦截」变成了「可自愈的纠错循环」。

### 4.2 我实测过的拦截效果（可直接说给面试官听）

| 攻击尝试 | 拦截结果 | 拦截层 |
|---|---|---|
| `UPDATE user SET balance=0` | 拒绝 | 语句类型判定 |
| `SELECT * FROM user; DROP TABLE user` | 拒绝 | 多语句切分 |
| `SELECT * FROM user -- comment` | 拒绝 | 危险片段正则 |
| `SELECT * FROM information_schema.tables` | 拒绝 | 危险片段正则 |
| `SELECT * FROM role` | 拒绝 | 表名白名单 |
| `SELECT ... FROM user UNION SELECT ... FROM information_schema.tables` | 拒绝 | 危险片段正则 |

> 我还验证过一个边界情况：`WITH t AS (SELECT 1) SELECT * FROM t` 这种 CTE 写法，sqlparse 的 `get_type()` 依然返回 `SELECT`，所以是**放行**的——这是正确的，CTE 本身不危险。但要注意 CTE 里如果引用了白名单外的表（比如 `WITH x AS (SELECT * FROM role) SELECT * FROM x`），我的表名提取正则只匹配 `from|join|into|update` 关键字后面的标识符，**`FROM x` 里的 x 是 CTE 名不是真实表名**，而 `FROM role` 在 CTE 内部也会被匹配到，所以这个场景是能拦住的。但如果是 `WITH x AS (SELECT * FROM (SELECT * FROM role) t) SELECT * FROM x` 这种嵌套形式，正则仍能扫到 `role`，也能拦住。
>
> 不过我要承认一个**已知的理论边界**：正则提取表名不是 SQL 解析器，遇到极端嵌套或者畸形语法可能漏检。更严格的方案是用 sqlparse 的 AST 或者直接用 MySQL 的 `EXPLAIN` 预检 + 只读数据库账号兜底。**最彻底的方案是给 NL2SQL 用一个独立的 MySQL 只读账号，只有 SELECT 权限**——那才是最后一道防线，代码层的白名单是第二道。我这两层都做了，但生产环境我会优先保证数据库账号层面的只读。

### 4.3 面试官可能追问 + 标准答法

**Q1：为什么不用参数化查询或者 ORM，偏要自己写 NL2SQL？**

> 因为用户问的是「本月陪玩师营收排行」这种**聚合型、跨表、维度未知**的问题，参数化查询解决不了——你没法预判用户会问什么。
> 预置指标工具（`get_order_trend`、`get_companion_ranking` 等）覆盖了高频问题，但覆盖不了长尾的自由查询，所以需要 NL2SQL 兜底。
> 我的设计是**双层**：高频走预置工具（安全、口径准、速度快），长尾才走 NL2SQL。这样 90% 的问题根本不需要让模型碰 SQL。

**Q2：LLM 生成的 SQL 不确定，你怎么保证它不删数据？**

> 三层防线，前面讲过。再强调一点：**我的表名白名单只有 16 张只读业务表，而且完全不包含任何权限表**。即使前两层被绕过，模型能操作的表也是明确枚举出来的。
> 最外层还有数据库账号本身的权限——这是我认为最应该做但当前没做的一层。

**Q3：有没有测试用例验证沙箱？**

> 我做的是**手工攻击用例验证**——我列了上面那张表，把常见的注入手法逐个跑过一遍确认拦截。这个我实际做了。
> 但自动化测试没写，这是个欠债。生产化应该写一套参数化的攻击语料测试集，每次改 `_validate` 逻辑就回归一遍。安全代码没有自动化测试是危险的。

**Q4：SQL 里的业务口径怎么保证一致？比如「成交订单」怎么定义？**

> 口径是写在两处的：**代码常量**和 **给 LLM 的 schema 说明**。
> 比如成交口径是 `status in (booked, ongoing, completed, refunding)`——这四个状态算成交，`pending`（待支付）和 `cancelled`（已取消）不算。
> 这个口径在 `sql_tools.py` 的 `_TABLE_SCHEMAS` 描述里明确告诉了 LLM，同时 `stat_tools.py` 里预置指标工具用的是同一套常量。两边保持一致。
> 我特意把口径说明放进 schema 描述里，是因为 LLM 不知道 `booked` 是什么意思，光看字段名它会猜错。

**Q5：多 Agent 之间会共享数据吗？会不会 A 把 B 的数据传给 C？**

> 会共享消息列表，这是 Supervisor 的设计。但**共享的是对话内容，不是数据访问权限**。每个子 Agent 的工具权限是代码层面绑定的——order_agent 只能查订单，recommendation_agent 只能查陪玩师，sql_agent 只能查白名单表。LLM 传话传不出权限。
> 这也是我坚持「安全在执行层」的原因：**上下文是共享的，但权限不是**。

## 5. 逐条讲解：简历第五句「流式交互」

### 5.1 怎么讲

> SSE 这块我用了一个我觉得挺巧的技巧。
>
> 首先说明为什么用 SSE 不用 WebSocket：**AI 对话是单向的**——用户发一条，服务器流式返回。WebSocket 的双向能力在这里用不上，而 SSE 基于 HTTP、自带断线重连、对 Nginx 和浏览器都更友好。实时双向聊天我另外用了 WebSocket。
>
> 协议我定义了四种事件：`status`（工具调用/Agent 移交进度）、`token`（Token 增量文本）、`done`（结束，带会话ID和标题）、`error`（异常）。
>
> 后端用的是 LangGraph 的 `astream_events(version="v2")`，这是官方的通用流式事件接口。选它而不是 `astream(stream_mode="messages")` 的原因是：**`astream` 对 supervisor 这种嵌套子图拿不到 token 级的流**，`astream_events` 能穿透嵌套拿到 `on_chat_model_stream`。
>
> **最关键的一个技巧是 token 归属的识别。** 子 Agent 和主管都会产生 LLM 输出，如果全发出去，用户会看到「我给你推荐以下陪玩师……」然后主管又说「根据以上推荐……」——内容重复且割裂。
> 我的解法是从事件元数据里取 `checkpoint_ns`（子图命名空间），它的首段就是产出这个 token 的节点名：主管是 `supervisor`，子 Agent 是它的注册 key。所以我维护一个子 Agent key 集合，**只透出不属于子 Agent 的 token**，子 Agent 的中间输出全部丢弃。这样用户看到的只有主管最终整合后的答案。
>
> 还有一个配套细节：**移交时的 reset 事件**。主管在决定移交前可能已经吐了一部分文案（比如「好的，我来帮你查」），移交后这段就不是最终答案了。我检测到 `answer_text` 非空就发一个带 `reset: true` 的 token 事件，前端收到就清空重画，保证最终输出干净。
>
> **心跳保活**：我用一个 `asyncio.Queue` 把「事件产出」和「事件发送」解耦——后台协程往队列里放事件，消费协程 `wait_for(queue.get(), timeout=15)`，超时了就发一个 `: ping` 注释行。这是 SSE 标准的注释形式，前端会忽略它，但能防止 Nginx/Vite 代理因为空闲把连接掐掉。关键是**心跳不影响产出**——如果直接在生成器里写等待逻辑，模型思考的 15 秒里就发不出任何东西了。
>
> 前端因为要用 POST 带 body（EventSource 不支持 POST），所以是 `fetch` + `ReadableStream` 手写 SSE 解析：累积 buffer、按空行切帧、解析 `event:` 和 `data:` 行、忽略注释行。

### 5.2 面试官可能追问 + 标准答法

**Q1：SSE 和 WebSocket 你都用了，为什么不统一？**

> 按场景分的：
> - **AI 对话**用 SSE：单向流、HTTP 语义、自带重连、走网关/代理友好
> - **实时聊天**用 WebSocket：真正的双向，用户和陪玩师要同时收发，而且需要在线状态
>
> 如果强行统一用 WebSocket 做 AI 对话，就得自己实现重连、心跳、消息边界，比 SSE 复杂且没有收益。反过来用 SSE 做聊天，接收方向没问题，但发送方向要再开一条 HTTP 长连接做 POST，做不到真正的实时。
> 这不是技术选型偏好，是按数据流向选型。

**Q2：`astream_events` v2 和 v1 有什么区别？为什么用 v2？**

> v2 是 LangGraph 官方当前主推的接口，事件结构更规范（`on_chat_model_stream`、`on_tool_start` 这类标准事件名），v1 是早期版本，事件命名和数据结构都有差异，很多场景下拿不到 token 级流。
> 官方文档也明确推荐 v2。

**Q3：`checkpoint_ns` 这个字段你怎么理解？为什么它能区分主管和子 Agent？**

> LangGraph 里每个节点执行时都会记录自己所处的「命名空间路径」。在顶层图里执行，命名空间是空的；进入某个子图/节点后，命名空间是 `节点名:uuid` 这种形式，多层嵌套会用 `|` 连接。
> 所以我取首段：`checkpoint_ns.split(":")[0].split("|")[0]`，得到的就是产出该 token 的节点名。
> 主管节点叫 `supervisor`（我在 `build_supervisor` 里通过 `supervisor_name="supervisor"` 固定的），子 Agent 节点名就是我在注册表里的 `key`（比如 `order_agent`）。所以我拿注册表里非主管的 key 做成集合，一判断就知道这个 token 是谁的。

**Q4：流式过程中模型报错了怎么办？**

> 我的处理是：SSE 一旦返回 200 头，HTTP 状态码就改不了了，所以**业务错误走事件而不是状态码**。生成器里 try/except 捕获所有异常，统一转成 `error` 事件，前端收到后展示错误提示。
> 同时 `finally` 里做了清理：如果客户端提前断开（生成器被取消），会 `producer.cancel()` 掉后台产出协程并等待它退出，避免协程泄漏。这是流式场景特有的资源管理问题。

**Q5：前端怎么解析 SSE？为什么要手写？**

> `EventSource` 只支持 GET，不能带请求头和 body。我的对话接口需要 POST JSON body（带 token 头、会话ID、消息内容），所以只能用 `fetch` + `ReadableStream`。
> 手写解析的关键点有三个：
> 1. **buffer 累积**：网络分片不会对齐 SSE 帧边界，必须累积后按 `\n\n` 切帧
> 2. **TextDecoder 用 `{stream: true}`**：多字节 UTF-8 中文可能被切在中间，不加这个参数会乱码
> 3. **解析失败要吞掉**：单个残包解析失败不能让整个流崩掉

## 6. 逐条讲解：简历第六句「实时通讯」

### 6.1 怎么讲

> 实时通讯我做的是两条独立通道，连接池也是分开的，互不影响：
>
> **官方客服通道**：`/ws/chat`（用户端）和 `/ws/adminChat`（客服/管理员端）。用户发消息落库后推给所有在线客服，客服回复落库后推给对应用户**和所有在线客服**（多工作台同步）。
>
> **用户私聊通道**：用户端连接池 + 陪玩师工作台连接池 + 监管管理员池。用户给陪玩师发消息推给陪玩师，陪玩师回复推给用户。
>
> 持久化层面有四张表：`service_conversation`/`service_message` 和 `private_conversation`/`private_message`，会话和消息分离存储。未读数存在会话表的 `user_unread` 字段上。
>
> **未读处理**：客服每回复一条，对应会话的 `user_unread` 加一；用户打开会话时调 REST 接口批量置零。这里我特意做成**「读消息」和「清未读」两个独立动作**——如果打开会话就自动清零，那用户在消息列表看到未读角标、点进去就没了，但实际可能还没看；分开之后未读是真实语义的。
>
> **WebSocket 鉴权**：浏览器 WebSocket API 不能自定义请求头，这是个坑。我的做法是 token 走 **query 参数**，然后复用 HTTP 那套校验逻辑（解析 → 黑名单 → 有效期），失败用不同的关闭码区分：4401 是未登录/过期，4403 是非客服端。
>
> **连接管理**用进程内存的字典池，同一个 user_id 重复连接会把旧连接踢掉，保证一个人只有一条活跃连接（避免消息重复收到）。推送失败就把连接从池里摘掉。

### 6.2 面试官可能追问 + 标准答法

**Q1：连接池在内存里，多实例部署会怎样？**

> 这是我的已知短板。内存池意味着**用户 A 连到实例 1、用户 B 连到实例 2 时，A 发消息 B 收不到**。
> 生产化的标准方案是引入 Redis Pub/Sub：每个实例订阅一个频道，本地收到消息后推给自己池里的连接；连接注册信息也放 Redis 的 Hash 里做全网路由。
> 当前是单进程部署（uvicorn 默认单进程），所以能用。我也在代码注释里明确标注了「与 token 黑名单同约束：仅单进程部署有效」。

**Q2：消息怎么保证不丢？**

> 当前是**先落库再推送**的顺序。落库成功才推，所以**已推出去的消息一定在库里**——保证了「收到了就不会丢」。
> 反过来，「库里有但没推到」是可能的（比如对方不在线）。这种情况靠**离线补偿**兜底：对方上线时通过 REST 接口拉取历史消息，同时 WebSocket 握手时回推当前未读数。
> 更严格的方案是引入消息队列做可靠投递 + 消费确认。我没做，因为这个场景的可靠性要求还没到那个级别。

**Q3：怎么知道对方在线？未读数怎么算？**

> 在线状态是**隐式的**——池里有连接就是在线，不在线就推送时静默忽略。
> 未读数存在会话表上，不是在内存里计数。因为要跨进程/跨重启保持，且用户可能同时有多个端。
> 打开会话时清零是走一个独立的 REST 接口（`PUT /chat/read`），批量把该用户所有会话的 `user_unread` 置 0。

**Q4：WebSocket 断开怎么检测？会不会有僵尸连接？**

> `WebSocketDisconnect` 异常会在 `receive_json` 时抛出，我在 `finally` 块里清理连接。
> 僵尸连接（比如网络断了但服务端没感知）靠**心跳**：客户端定期发 `{"type":"ping"}`，服务端回 `{"type":"pong"}`。但严格说，服务端侧还需要一个超时清理机制——如果客户端不发心跳，服务端应该在 N 秒无消息后主动断开回收。这个我目前没实现，是个可以补的点。

## 7. 逐条讲解：简历第七句「管理后台」

### 7.1 怎么讲

> 管理后台基于 Vue3 + Tailwind CSS 4 + ECharts 6，主要做了两块：**数据看板**和**运营管理**。
>
> 看板部分用 ECharts 做交互式图表，指标和 Agent 侧的 `stat_tools.py` 是**同一套口径**——看板显示的数和分析 Agent 说的数必须一致，这个我在设计时特意对齐过。

> 运营功能包括：陪玩师审核（认证/状态管理）、订单监管（状态流转、退款确认）、投诉处理、优惠券管理、公告/FAQ/反馈管理，以及 **Agent 动态管控**——这个比较特别，管理页能直接编辑每个 Agent 的提示词、温度、启停状态，还能看到近 30 天的调用次数。
>
> 权限上用的是**动态路由**：登录后拿菜单接口返回的树，根据角色过滤过的菜单动态 `addRoute`。所以不同角色登录后台，左侧菜单和可访问页面完全不一样。

### 7.2 面试官可能追问 + 标准答法

**Q1：动态路由怎么实现的？**

> 后端 `menu_service` 按 `role_id` 查 `role_menu` 关联表过滤菜单，返回一棵 `children` 树。前端拿到后遍历，一级目录生成 Layout 下的子路由，顶级菜单直接挂 Layout，路径按规则拼（目录加 `/` 前缀）。
> 权限控制是**前后端双重**的：前端菜单控制只是「看不见」，真正的拦截在后端——每个管理接口都做角色校验，非管理员调用直接抛业务异常。前端隐藏按钮不等于安全，后端校验才是。

**Q2：看板数据怎么来的？实时还是定时？**

> 当前是**接口实时查询**。用户打开看板，前端并发请求几个统计接口，后端查 MySQL 聚合后返回。
> 数据量小的时候这样最简单，也最实时。数据量大或者看板访问频繁的话，应该改成预聚合——比如定时任务把订单按天/小时预统计进汇总表，看板直接查汇总表。牺牲实时性换查询性能。

**Q3：ECharts 用的什么版本？为什么选它？**

> ECharts 6。相比 5，6 在响应式和自定义渲染上做了改进，也更适配 Vue3 的生命周期。
> 选它的原因主要是**开箱即用**：折线图、柱状图、饼图、仪表盘这些经营看板常用图类型都有，交互（tooltip、legend、缩放）都是内置的，不需要自己写。

## 9. 高频技术追问速查

### Python / 后端

**Q：为什么用 FastAPI 不用 Django/Flask？**
> FastAPI 的 Pydantic 类型注解能自动做请求校验和生成 OpenAPI 文档，异步原生支持 SSE 和 WebSocket。Flask 是同步的，做流式要绕路；Django 太重，我这个项目本质是 API 服务，没有 Django 的 ORM Admin 和模板系统需求。

**Q：SQLAlchemy 2.0 的 `Mapped[]` 语法和老的写法区别？**
> 2.0 用 `Mapped[int] = mapped_column(...)` 的类型注解方式，类型信息写在左边，SQLAlchemy 能据此推导列类型，也更符合现代 Python 类型提示风格。老写法是 `id = Column(Integer, primary_key=True)`。2.0 还统一了 `select()` 查询风格，配合 2.0 的 `selectinload` 做关联预加载能避免 N+1 查询。

**Q：`expire_on_commit=False` 为什么这么设？**
> 默认 True 意味着 commit 之后对象属性会被过期，下次访问触发刷新查询。在 SSE 流式场景里，commit 后我还要继续读对象属性（落库后取会话标题等），设 False 可以避免多余的 SELECT。

**Q：为什么连接池要设 `pool_pre_ping` 和 `pool_recycle`？**
> `pool_pre_ping` 取连接前先探活，MySQL 的 `wait_timeout` 到了会断连，不探活就会拿到死连接报错。`pool_recycle=3600` 是定期回收，避免连接长期存活被中间设备断开。

### AI / Agent

**Q：Agent 和普通 Chatbot 的区别？**
> Chatbot 是单轮问答，Agent 具备**规划、调用工具、观察结果、迭代**的能力循环。我的子 Agent 用的是 LangGraph 的 `create_react_agent`，本质就是 ReAct（Reason + Act）循环：模型思考 → 决定调工具 → 执行 → 观察结果 → 继续思考，直到能给出最终答案。

**Q：ReAct 的循环是怎么终止的？**
> 模型不再发起工具调用时终止。另外 LangGraph 有 `recursion_limit` 兜底，防止模型陷入死循环反复调工具。

**Q：Function Calling / Tool Calling 的原理？**
> 模型本身不执行函数。是模型的接口约定：你在请求里把工具的 JSON Schema 描述给模型，模型返回「我要调这个函数，参数是这些」，真正的执行由你的框架完成，结果再作为 tool message 回传给模型继续推理。工具的 docstring 和参数类型描述就是给模型看的说明书——所以我每个工具的 docstring 都写得很详细，包括参数含义和取值范围。

**Q：你怎么防止 LLM 调工具时传错参数？**
> 靠 Pydantic 类型注解自动生成 schema + LangChain 的参数校验，参数不合法会直接报错。同时 docstring 里写清取值范围（比如 `status` 的六个合法值）。
> 另外工具返回值我统一用 JSON 字符串而不是对象，是因为不同 LLM 对复杂对象返回的序列化稳定性有差异，字符串更可靠。

**Q：为什么温度设置成这样？**
> 主管 0.3——路由决策要稳定，0.7 以上容易飘。推荐 Agent 0.5——推荐话术需要一点多样性和个性化。订单/FAQ 0.1——查账和讲规则必须准确，不能发挥。SQL Agent 0.0——生成 SQL 要完全确定，温度必须为 0，否则同一问题两次生成的 SQL 不一样，缓存和复现都成问题。

### 系统设计 / 综合

**Q：如果流量涨 100 倍你会怎么改？**
> 分四层：
> 1. **无状态化**：Token 黑名单和 WS 连接池从内存搬到 Redis，这是多实例的前提
> 2. **数据库**：加读写分离，看板/统计查询走从库；订单列表这种深分页改游标分页
> 3. **缓存**：陪玩师列表、FAQ、游戏分类这些读多写少的加 Redis 缓存；NL2SQL 的 schema 说明也可以缓存
> 4. **异步化**：消息投递走 MQ；统计预聚合落汇总表；Agent 图按配置版本号缓存

**Q：这个项目如果只让你保留一个亮点，你选哪个？**
> 我选 **NL2SQL 安全沙箱**。因为它体现的不是「我用了某个框架」，而是「我知道这类技术的风险边界在哪，并且用多层机制把风险压下去了」——而且每一层都有实测证据。技术栈谁都会用，能讲清楚「为什么这样设计、边界在哪、怎么补」的才是有工程能力的。

## 附：技术亮点速记（面试官点赞的六个点）

1. **安全约束在执行层，不在提示词层** —— NL2SQL 五层沙箱 + 订单工具闭包绑定 user_id
2. **校验失败不抛异常，把错误交还 LLM 自愈** —— 把安全拦截变成可纠错循环
3. **`checkpoint_ns` 区分 token 归属** —— 子 Agent 中间输出不污染最终答案
4. **产出与心跳解耦的 asyncio.Queue** —— 15 秒无产出补 ping，且不阻塞模型输出
5. **DB 读失败 → 字段回退 → Agent 停用 → 全停用降级，四层容错** —— 任何一层配置异常都不 500
6. **代码是唯一事实来源，DB 只覆盖运行时可变部分** —— 工具清单不可后台篡改，安全边界不被绕过
