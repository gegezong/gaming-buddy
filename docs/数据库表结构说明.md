# 数据库表结构说明（28 张表）

> 库名 `gaming-buddy` · MySQL 8.0 · InnoDB · utf8mb4 / utf8mb4_bin
> 建表脚本：`gaming-buddy.sql`（Navicat 导出，含 28 张表 + 442 行种子数据）
> ORM 映射：`fastapi/models/entities.py`

## 速览

| 模块 | 表数 | 表 |
|---|---|---|
| 用户与权限 | 4 | `user` `role` `menu` `role_menu` |
| 陪玩与内容 | 6 | `companion` `companion_game` `companion_service` `game_category` `service_item` `banner` |
| 交易与订单 | 2 | `companion_order` `complaint` |
| 营销与资金 | 5 | `coupon` `user_coupon` `wallet_transaction` `gift` `reward` |
| 沟通服务 | 5 | `private_conversation` `private_message` `service_conversation` `service_message` `follow` |
| 运营与 AI | 6 | `notice` `faq` `feedback` `agent_config` `agent_conversation` `agent_message` |

## 一、用户与权限（4 张）

RBAC 的底座：`user` 挂角色，角色挂菜单，菜单决定前端能看见哪些页面。

### `user` — 用户
全系统的身份主表，35 个账号。

| 字段 | 说明 |
|---|---|
| `user_id` | 主键 |
| `user_name` | 登录用户名，唯一 |
| `password` | **明文密码**（登录直接比对，`routers/auth.py:45`），生产必须改哈希 |
| `role_id` | 角色 ID，指向 `role` |
| `balance` | 钱包当前余额（元，整数） |
| `sex` / `avatar` / `create_time` | 性别 / 头像 URL / 注册时间 |

> 一张表同时承载四种身份：管理员（role_id=1）、普通用户（2）、陪玩师（3）、客服（4）。
> 陪玩师有独立的资料表 `companion`，通过 `companion.user_id` 关联回来——`user` 是身份，`companion` 是职业档案。

### `role` — 角色
| 字段 | 说明 |
|---|---|
| `role_id` | 主键 |
| `role_name` | admin / user / companion / service |
| `role_sort` | 展示排序 |
| `remark` | 备注 |

### `menu` — 菜单
| 字段 | 说明 |
|---|---|
| `menu_id` / `parent_id` | 自关联，`parent_id=0` 为顶级目录 |
| `path` / `component` | 前端路由地址 / 组件路径 |
| `menu_type` | `M` 目录 / `C` 菜单 |
| `icon` / `menu_sort` | 图标 / 排序 |

### `role_menu` — 角色菜单关联
`(role_id, menu_id)` 多对多。**没有外键约束**，靠代码维护，所以改权限时两个表要一起动。

> 后端：`routers/auth.py` `routers/user.py` `routers/role.py` `routers/menu.py` → `services/user_service.py` `role_service.py` `menu_service.py`

## 二、陪玩与内容（6 张）

C 端商城的商品侧：谁能被约、用什么价位、能玩什么游戏。

### `companion` — 陪玩师
32 位陪玩师的职业档案。

| 字段 | 说明 |
|---|---|
| `companion_id` | 主键 |
| `user_id` | 关联 `user`，陪玩师同时也是平台用户 |
| `nick_name` | 昵称，唯一 |
| `gender` / `age` / `city` | 性别(0男1女) / 年龄 / 城市 |
| `voice` | 声线（甜音、御姐…），平台卖点 |
| `price` | 起步价（元/小时） |
| `intro` / `tags` | 简介 / 标签（逗号分隔） |
| `certified` | 认证状态 |
| `status` | 0 启用 / 1 停用 |
| `main_game_id` / `main_rank` | 主游戏 / 主段位 |

### `game_category` — 游戏分类
15 款游戏。名字叫 category 但实际是"可约玩的游戏清单"：`game_name` 唯一，含图片、标签、排序。

### `service_item` — 服务项目
平台服务目录（19 项）：上分陪练、语音哄睡、语音倾听…每项有图片、描述、排序。**平台级**定义。

### `companion_service` — 陪玩师服务关联
`(companion_id, service_id)` 多对多，中间带 `price`——同一项服务，不同陪玩师定价不同。105 条，是全库行数最多的关联表。

### `companion_game` — 陪玩师游戏关联
`(companion_id, game_id)` 多对多，中间带 `game_rank`——这位陪玩师玩某游戏到什么段位。96 条。

### `banner` — 首页轮播图
4 条。`image` + `bg_color`/`fg_color`（图片缺失时的回退配色）+ `link_url`/`link_text`（点击跳转）。

## 三、交易与订单（2 张）

### `companion_order` — 陪玩订单
**全库最核心的表**，29 个字段，把下单、支付、履约、评价四段生命周期压在一行里。

| 分段 | 字段 |
|---|---|
| 标识 | `order_id` `order_no`（GB 开头唯一）`user_id` `companion_id` `service_id` |
| 快照 | `service_name` `price` `coupon_name` `coupon_amount`——**下单瞬间把名称和价格冻结**，后续服务改名改价不影响历史订单 |
| 金额 | `gross_amount`（原价=单价×时长）`amount`（实付）`hours` `service_date` `start_hour` |
| 支付 | `pay_method`（balance/wechat/alipay）`pay_time` `status` |
| 履约 | `start_time` `end_time` `cancel_reason` |
| 评价 | `review_rating` `review_tags` `review_content` `review_time` `review_reply` `review_reply_time` |

**状态机**：`pending`（待支付）→ `booked`（待开始）→ `ongoing`（进行中）→ `completed`（已完成）；旁支 `refunding`（退款中）、`cancelled`（已取消）。

> 结算口径：Agent 的经营分析把 `booked/ongoing/completed/refunding` 视为"成交"。

### `complaint` — 订单投诉
| 字段 | 说明 |
|---|---|
| `order_id` | **唯一约束 → 每单只能投诉一次** |
| `complaint_type` | 服务态度差 / 迟到未服务 / 技术不符 / 诱导私下交易 / 言语不当 / 其他 |
| `status` | 0 待处理 / 1 已处理 |
| `handle_result` | 警告陪玩师 / 全额退款 / 驳回 / 其他 |
| `reply` / `handle_time` | 平台处理说明 |

## 四、营销与资金（5 张）

### `coupon` — 优惠券模板
`amount` 面额 + `threshold` 门槛（0 无门槛）+ `valid_days` 有效期 + `per_limit` 每人限领 + `total_count` 发放总量（0 不限）。

### `user_coupon` — 用户领到的券
`coupon` 模板 + 用户实例。`status` 只有 0 未使用 / 1 已使用，**过期不落状态，靠 `expire_time` 动态判定**——这是本项目一个值得注意的设计取舍。

### `wallet_transaction` — 钱包流水
| 字段 | 说明 |
|---|---|
| `type` | recharge 充值 / consume 消费 / refund 退款 / reward 打赏 / adjust 人工调整 |
| `amount` | 变动金额，正收负支 |
| `balance_after` | **变动后余额快照**，可对账可回溯 |
| `operator` | 人工调整时记管理员名 |

> 余额当前值只在 `user.balance`；这张表是账本。两者在同一事务里写，代码见 `services/order_service.py` / `wallet_service.py`。

### `gift` — 打赏礼物
礼物目录（4 项）：名称、图片、价格、排序。

### `reward` — 打赏记录
`user_id` + `companion_id` + 礼物名/图快照 + 金额。同时给陪玩师加余额、给用户扣余额。

## 五、沟通服务（5 张）

两套结构完全平行的聊天系统：用户↔陪玩师、用户↔官方客服。

### `private_conversation` / `private_message` — 用户私聊
- 会话表：`user_id` + `companion_id`，`last_message` 快照（列表展示免查消息表）、`user_unread` / `companion_unread` 双向未读数、`last_time` 排序。
- 消息表：`sender_type`（0 用户 / 1 陪玩师）、`content`、时间。
- 走 **WebSocket** 实时推送（`core/ws.py`）。

### `service_conversation` / `service_message` — 官方客服
同一套结构，但会话表只有 `user_id` 且**一人一会话**（唯一约束），没有陪玩师维度，也没有反向未读数（客服侧在管理端看）。

### `follow` — 用户关注陪玩师
`(user_id, companion_id)` + 关注时间，极简关注关系。

## 六、运营与 AI（6 张）

### `notice` — 平台公告
标题 + 类型（保障/活动/上新/安全）+ 正文 + 发布状态。Agent 的 `list_notices` 工具读它。

### `faq` — 帮助中心
分类（新手指南/下单支付/服务保障）+ 问题 + 答案 + 排序。Agent 的 `search_faq` 工具读它。

### `feedback` — 意见反馈
类型 + 内容 + 处理状态 + 平台回复。

### `agent_config` — Agent 配置
**本项目的 AI 灵魂表**。7 个 Agent 各一行：

| 字段 | 说明 |
|---|---|
| `agent_key` | 标识，如 `supervisor_user` `sql_agent` |
| `scene` | `user` 用户端 / `analyst` 管理端 |
| `prompt` | 系统提示词，**管理页可改，下次对话生效** |
| `tools` | 工具清单（只读展示，实际由代码注册决定） |
| `temperature` | 采样温度 0~1 |
| `enabled` | 0 启用 / 1 停用（停用即该 Agent 不参与编排） |

> 代码侧的注册表在 `fastapi/agent/registry.py`，是"唯一事实来源"；DB 只覆盖运行时可变部分（提示词/温度/启停）。

### `agent_conversation` / `agent_message` — AI 对话记录
- 会话：`user_id` + `scene` + `title`（首轮自动取用户输入前 20 字）+ `update_time`（活跃时间）。
- 消息：`role`（user/assistant）+ `agent_name`（**这条回复主要由哪个 Agent 贡献**）+ `content`。
- `agent_name` 聚合起来就是"近 30 天各 Agent 调用次数"（`services/agent_service.py` 的 `agent_call_stats`），管理页的 Agent 调用统计就是这么来的。

## 几个贯穿全库的约定

| 约定 | 说明 |
|---|---|
| 金额 | 一律 `int` 存"元"，不用浮点，避免精度问题 |
| 状态字段 | `status` 语义在不同表里不同：0 可能是"启用"也可能是"待处理"，看注释 |
| 快照字段 | 订单、评价、打赏都保留下单/打赏瞬间的文本与价格 |
| 外键 | **大部分关联没有真实外键约束**，靠应用层保证；只有 `order_no` `user_name` `game_name` 等用了唯一索引 |
| 逻辑删除 | 没有软删字段，删除即物理删除 |
| 时间 | `create_time` / `update_time` 为 `datetime`，无时区 |

## 想改数据结构时

1. 改 `gaming-buddy.sql`（保持与实体一致）
2. 改 `fastapi/models/entities.py`（ORM 实体）
3. 改对应的 `services/*.py` 和 `routers/*.py`
4. 重新导入 SQL 或写增量 `ALTER TABLE`
5. `services/agent_service.py` 的 `get_effective_configs` 会在表不存在时回退代码默认值，所以 Agent 模块在没建表时也能跑
